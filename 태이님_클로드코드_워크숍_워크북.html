1.1 클로드 코드란?

개념클로드 코드 = 내 컴퓨터에서 직접 일하는 AI 비서

일반적인 AI 챗봇(ChatGPT 등)은 대화만 해요. 클로드 코드는 달라요. 내 컴퓨터의 파일을 직접 읽고, 만들고, 수정하고, 명령을 실행해요.

알아야 할 명령어는 딱 하나: claude

개념ChatGPT와 뭐가 다른가요?

기능ChatGPT클로드 코드비고
파일 접근
(File Access)		불가내 컴퓨터 파일을 직접 읽고 수정할 수 있음
기억력
(Memory)		대화가 끝나면 사라짐프로젝트 설정 파일에 저장해서 다음에도 기억함부록 참고
실행력
(Execution)		지시한 작업을 실행지시한 목표를 달성
동시 작업
(Parallel)		한 번에 하나씩 처리여러 작업을 동시에 처리 가능
에이전트
(Agent)		단일 인스턴스역할별 전문 에이전트로 분업 가능3.1

각 기능을 좀 더 풀어볼게요:

  1. 파일 접근 · ChatGPT는 대화창 안에서만 동작하지만, 클로드 코드는 내 컴퓨터의 폴더와 파일을 직접 다룰 수 있어요.
  2. 기억력 · ChatGPT는 대화를 닫으면 이전 맥락을 잊지만, 클로드 코드는 CLAUDE.md라는 설정 파일에 프로젝트 정보를 저장해서 다음 대화에서도 기억해요.
  3. 실행력 · ChatGPT는 지시한 단일 작업을 실행하지만, 클로드 코드는 지시한 목표를 스스로 분해하고 기획부터 구현까지 자동화해요. 예를 들어 "IG 성장 데이터 분석 레포트를 만들어줘"라고 하면, 데이터 수집 → 가공 → 시각화 → HTML 생성까지 스스로 판단하며 워크플로우를 구축합니다.
  4. 동시 작업 · ChatGPT는 하나의 요청을 순서대로 처리하지만, 클로드 코드는 여러 작업을 동시에 처리할 수 있어요.
  5. 에이전트 · ChatGPT는 하나의 AI가 모든 것을 처리하지만, 클로드 코드는 기획·실행·검수처럼 역할별 전문 에이전트를 두고 분업할 수 있어요.

핵심 차이 · ChatGPT도 실무에 활용할 수 있지만, 새 대화를 시작할 때마다 프로젝트 맥락, 선호사항, 용어 등을 매번 다시 설명해야 해요. 이것을 재설명 문제(Re-Explanation Problem)라고 합니다. 클로드 코드는 CLAUDE.md에 이 정보를 저장해두기 때문에, 매번 처음부터 설명할 필요 없이 바로 작업을 이어갈 수 있어요.

개념슬래시 명령어 한눈에 보기

세션 관리 (가장 많이 씀)

명령어하는 일
/clear대화를 초기화합니다. 파일은 그대로 유지돼요. 대화가 길어져서 새 작업으로 넘어갈 때 사용해요

/resume클로드 코드를 껐다 켜도 이전 대화를 복원해요. 퇴근 후 다음날 이어서 작업할 때 유용합니다

개념3가지 입력 모드

모드설명언제 쓰나요?

개념Think 키워드

클로드 코드는 내 지시나 요청사항에 따라 자동으로 적합한 생각 깊이를 골라서 답변해요. 아래 키워드를 프롬프트에 넣으면 원하는 생각 깊이를 직접 지정할 수도 있어요. 여러 관점을 따져야 하는 결정에 유용해요.

키워드언제 쓰나요?생각 시간·비용
think 간단한 비교·정리. "이 두 문구 중 어느 게 더 끌려?" 같은 가벼운 판단 기본보다 약간 증가
think hard / think harder 여러 요소를 동시에 고려해야 하는 결정.

예: "이번 주 IG 도달이 떨어졌어. KPI 데이터 보고 원인 가설 3개 뽑아줘 — 콘텐츠 톤·발행 시간·해시태그 다 고려해서"

예: "이 PRD 다 썼는데 내가 놓친 부분 있을까? 기획자 관점으로 다시 봐줘"

예: "이 리포트 초안에 법률적으로 문제 될 표현 있는지 꼼꼼히 봐줘" 		중간 정도 증가
ultrathink 실수하면 되돌리기 어려운 중요 결정.
예: 브랜드 네이밍 후보 최종 3개 압축, 공식 발표 전 전체 캠페인 리뷰		 크게 증가 (응답 느려지고 비용 많이 들어감)
참고: 세 단계는 Anthropic 엔지니어링 블로그에서 공개된 패턴이에요. 내부적으로 쓰는 "생각 토큰" 예산이 점점 커진다고 알려져 있지만, 정확한 숫자는 공식 문서에 명시되어 있지 않아요.

실습 2세션 관리 3종 체험

작업이 길어지면 클로드 코드가 컨텍스트 부족을 알려줘요. 이때 /compact(이어가기) 또는 /clear(초기화)로 해결할 수 있어요.

/cost 입력 → 현재까지의 비용을 확인

2.1 API란? — "약속·창구·출입증"

개념비유로 한 번에 잡기

실무에서 데이터를 자동으로 다루다 보면 "API"라는 단어를 자주 만나요. 어렵게 들리지만, 핵심만 풀어보면 이거예요.

개념비유실제 의미
API 인스타 사장님이 정해놓은 창구 외부 서비스(인스타·국토부·구글 등)가 우리에게 데이터를 주고받기 위해 정해 놓은 약속된 통로예요. 사장님께 매일 직접 가서 받아 적는 게 아니라, 사장님이 만든 창구로 요청하면 정해진 형식으로 데이터를 보내줘요.
API 키 창구를 쓰기 위한 출입증 아무나 데이터를 빼갈 수 없도록, 등록한 사람에게만 발급되는 개인 식별자예요. 비밀번호처럼 취급해요(다른 사람에게 절대 공유 X).
API 호출 창구에 요청서를 내미는 것 "2026-04-21 도달 데이터 주세요"처럼, 정해진 형식의 요청을 보내면 JSON이라는 깔끔한 표 형태로 답이 와요.

오늘 만날 API 예시

  • Instagram Insights API — 인스타가 정해놓은 창구. 도달·DM·팔로워 같은 숫자를 받을 수 있어요. (오늘 KAI가 쓰는 API)
  • 국토부 실거래가 API — 국토교통부가 정해놓은 창구. 거래된 부동산 정보를 받을 수 있어요.
  • Google Calendar API — 구글이 정해놓은 창구. 일정 데이터를 받거나 만들 수 있어요.
오늘 워크숍에서 코드를 직접 짜진 않아요. "API라는 통로가 있다 → 그 통로로 받은 데이터를 클로드 코드가 분석한다" 흐름만 잡으시면 충분해요.

1) 에이전트 (Agent) — 독립적인 1급 실행 단위

위 표에서 Max, KAI, Luna가 각각 에이전트입니다. "이번 주 KPI 레포트 만들어줘"라고 요청하면, KAI가 스스로 데이터를 가져오고, 계산하고, HTML을 만들고, 차트를 그립니다. 사람이 매 단계를 지시하지 않아도 다음 할 일을 스스로 판단해요.

핵심: 에이전트는 독립적인 역할과 프롬프트를 가집니다.

  • 자기만의 전문 영역이 있음 (Max는 기획, KAI는 분석, Luna는 검수)
  • 스스로 판단해서 작업을 수행
  • 에이전트 = AI + 도구(Tools) + 판단력(Reasoning)

2) 서브에이전트 (Sub-Agent) — 임시 작업자

위 표에서 KAI 세부 내용에 "필요시 서브에이전트로 분리"라고 적혀 있어요. 서브에이전트는 에이전트가 작업 중 필요에 따라 임시로 생성하는 작업자입니다.

핵심: 서브에이전트는 임시예요. 메인 대화의 컨텍스트를 보호하기 위해 만들어집니다.

  • 메인 대화가 너무 길어지는 것을 방지
  • 무거운 작업을 분리해서 처리
  • 작업이 끝나면 결과만 남기고 사라짐

레포트 작성 과정에서 데이터 수집, 차트 생성, HTML 템플릿 채우기 등 여러 작업을 동시에 처리해야 합니다. 이때 KAI가 모든 것을 혼자 하면 대화가 길어지고 맥락이 흐려질 수 있어요. 그래서 KAI는 필요에 따라 서브에이전트를 임시로 생성해서 무거운 작업을 분리합니다. 예를 들어 일별 차트 SVG 생성은 서브에이전트에게 맡기고, KAI는 결과만 받아서 전체 레포트 조립에 집중하는 방식이에요.

3) 오케스트레이션 (Orchestration) — 전체 조율

위 표 전체가 오케스트레이션이에요. Max → KAI → Luna → 퍼블리시 순서로 누가, 언제, 무엇을 할지 전체 흐름을 설계하고 조율합니다.

오케스트레이션 패턴 5가지

패턴설명예시
Fan Out
(분산 처리)		같은 작업을 여러 파일에 동시 적용"15개 파일에서 각각 핵심 내용을 뽑아서 하나로 합쳐줘"
Specialized Roles
(역할 분담)		다른 역할의 에이전트가 각자 전문 분석"에이전트 1은 IG 분석, 에이전트 2는 카톡 분석, 에이전트 3은 블로그 분석"
Parallel Research
(병렬 조사)		여러 대상을 동시에 조사"경쟁사 5곳을 동시에 리서치해서 비교표 만들어줘"
Batch Generation
(대량 생성)		비슷한 문서를 대량 생성"이 PRD를 기반으로 사용자 스토리 20개 만들어줘"
Validation Pipeline
(검증 파이프라인)		여러 문서를 품질 기준으로 검수"docs 폴더의 모든 문서를 품질 체크리스트 기준으로 검토해줘"
그럼 이 에이전트들에게 "무엇을 해야 하는지"를 어떻게 지시할까요? 그것이 바로 PRD(제품 요구사항 문서)입니다. 다음 섹션에서 다룰게요.

체크포인트

  • 에이전트 / 서브에이전트 / 오케스트레이션의 차이를 이해함
  • KAI 레포트 파이프라인에서 각 개념이 어디에 해당하는지 파악함

3.2 PRD (제품 요구사항 문서)

개념PRD(Product Requirements Document)란?

3.1에서 에이전트의 개념을 배웠어요. 그런데 한 가지 빠진 것이 있어요. 에이전트에게 "무엇을 해야 하는지"를 어떻게 정확하게 전달할 것인가?

AI에게 "알아서 KPI 레포트 만들어줘"라고 하면 어떻게 될까요? 어떤 데이터 기간을 쓸지, 어떤 KPI 목표를 기준으로 할지, 어떤 디자인으로 만들지, 어떤 기준으로 품질을 판단할지 모두 AI가 임의로 결정하게 돼요. 결과물이 매번 달라지고, 원하는 품질을 안정적으로 얻기 어려워집니다.

이 문제를 해결하는 것이 바로 PRD(Product Requirements Document)예요. PRD는 AI 에이전트에게 주는 상세 업무 지시서로, 다음과 같은 핵심 항목들을 담고 있어요:

항목역할예시 (KAI 시스템)
목적이 시스템이 왜 필요한지"마케팅 KPI를 자동 추적하여 의사결정 사이클을 단축한다"
목표 지표성공을 어떻게 측정할지"월간 신규 적격 관심 유저 수, 주간 도달 ≥500, 참여율 ≥5%"
에이전트 구성누가 어떤 역할을 맡는지"기획자(Max), 분석가(KAI), 검수자(Luna)로 분리"
파이프라인작업이 어떤 순서로 흐르는지"데이터 수집 → 가공 → 시각화 → 검수 → 발행"
입출력 정의무엇을 넣고 무엇이 나오는지"IG Insights API + KPI 목표값 → 단일 HTML 대시보드"
품질 기준어떤 기준을 지켜야 하는지"숫자 정합성, 면책 문구 필수, 모바일 호환"

PRD가 잘 작성되어 있으면, AI 에이전트는 매번 일관된 품질의 결과물을 만들어낼 수 있어요.

개념REXA 마케팅 에이전트 PRD 살펴보기 — Session 2에서 체험한 작업의 뒷면

Session 2에서 직접 체험한 'KAI의 KPI 대시보드 파이프라인' 기억하시죠? IG 일별 데이터를 넣으면 HTML 레포트가 나오는 그 작업이에요.

그 작업이 안정적으로 돌아가려면 뒤에서 PRD가 모든 것을 정의하고 있어야 해요. REXA 마케팅 에이전트 PRD v2.0의 핵심 구조를 살펴볼게요.

항목내용
1. 개요목적: REXA 사전 마케팅 & 초기 유저 확보 / 핵심 가치: 마케팅 전담 인력 없이 AI 에이전트로 자동화
2. 전략 및 목표North Star Metric: 월간 신규 적격 관심 유저 수 / Input Metrics (Phase 1 IG): 주간 도달 500, 참여율 5%, 수신 DM 2건/주, HOT DM 1건/주
3. 에이전트 팀Max(매니저): 일일·주간 계획, KPI 추적 / KAI(Growth Analyst): 데이터 수집·분석·레포트 / Luna(검수): 품질 게이트, 법률 준수
4. 파이프라인데이터 수집 → 가공 → 시각화 → 검수 → 발행
5. 품질 기준숫자 정합성, 면책 문구, KPI 목표 대비 ✅/❌ 표시 일관성, 차트 가독성

PRD 안에 에이전트별 상세 스펙도 포함할 수 있어요. 예를 들어 REXA PRD에서는 각 에이전트의 사용 도구, 입출력, 판단 기준까지 정의하고 있습니다.

  • KAI (Growth Analyst): IG Insights API 데이터를 입력받아 KPI 대시보드 HTML과 위험 신호 알림을 생성. 숫자 정합성, 면책 문구 포함, 두 계정 합산 일관성을 품질 기준으로 따름.
  • Luna (검수): KAI의 결과물을 입력받아 승인 또는 반려를 판정. 80점 이상이면 자동 승인, 50~79점이면 사람 검토, 50점 미만이면 반려.

Claude Code에게 PRD를 요청하는 방법

PRD를 처음부터 직접 작성할 필요는 없어요. 클로드 코드에게 목적과 현재 상황을 간단히 설명하면, AI-Native 방식으로 함께 작성할 수 있어요.

클로드 코드에 입력
"나는 [자동화하고 싶은 업무]를 하고 있어.
현재는 [현재 작업 방식]으로 진행하고 있는데,
이걸 자동화하기 위한 PRD를 작성해줘."
구체적인 PRD 작성 실습은 3.4에서 직접 진행할 예정이에요. 위 예시와 REXA의 PRD를 참고하면서 함께 만들어 볼게요.

PRD와 CLAUDE.md의 관계

작성한 PRD를 CLAUDE.md 파일로 저장하면, 클로드 코드가 매 세션마다 자동으로 읽어요. 즉, PRD를 CLAUDE.md에 담아두면 매번 다시 설명할 필요 없이 클로드가 프로젝트 맥락을 기억한 상태로 작업을 시작합니다.

CLAUDE.md 활용법은 부록의 실무 팁을 참고해 주세요.

체크포인트

  • PRD가 왜 필요한지, 어떤 항목들이 들어가는지 이해함
  • Session 2에서 체험한 KPI 대시보드 파이프라인 뒤에 PRD가 있다는 것을 이해함

3.3 하네스 엔지니어링

개념하네스 엔지니어링이란?

하네스(Harness)란 AI 모델이 혼자서는 잘 못하는 부분을 보완하기 위한 운영 구조예요. 같은 AI 모델이라도, 어떤 구조 안에서 일하느냐에 따라 결과가 완전히 달라집니다. 이 운영 구조를 설계하는 것을 하네스 엔지니어링이라고 해요.

그렇다면 왜 이런 구조가 필요할까요? AI에게 일을 그냥 시키면 어떤 문제가 생기는지부터 살펴볼게요.

개념AI에게 일을 그냥 시키면 생기는 문제들

아래 내용은 Anthropic이 자체 기술 블로그에서 직접 공개한 내용이에요. (2026년 3월 24일 발행) 원문: anthropic.com/engineering/harness-design-long-running-apps

문제 1: 컨텍스트 불안 — 대화가 길어지면 AI가 대충 마무리한다

AI에게 긴 작업을 시키면, 처음에는 꼼꼼하게 수행해요. 하지만 대화가 길어질수록 앞에서 무엇을 했는지 점점 헷갈리기 시작하고, 실제로 한계에 도달하지 않았더라도 AI가 "이쯤이면 한계에 가까워졌겠지"라고 느끼면서 서둘러 끝내버리는 현상이 발생해요. Anthropic은 이 현상을 "컨텍스트 불안(Context Anxiety)"이라고 부릅니다.

문제 2: 자기 평가의 함정 — AI에게 자기 결과물을 평가하라고 하면 항상 후하게 준다

AI에게 콘텐츠를 만든 후 "방금 만든 결과물을 평가해봐"라고 요청하면, 품질이 부족하더라도 "아주 훌륭합니다!"라고 답하는 경우가 많아요. 자기가 만든 것을 객관적으로 비판하는 것은 AI에게도 어려운 일이에요. 특히 디자인처럼 주관적인 영역에서 이 문제가 더 심하게 나타나요.

개념해결책: 교대 근무 + Generator/Evaluator 역할 분리

해결책 1. 컨텍스트 불안 → Context Reset (교대 근무)

AI 에이전트 하나가 처음부터 끝까지 다 하지 않고, 구간을 나눠서 여러 에이전트가 교대로 작업합니다. 에이전트가 일정 구간을 작업한 뒤, 진행 상태와 다음 할 일을 파일로 저장하고 컨텍스트를 완전히 초기화해요. 그러면 새로운 에이전트가 해당 파일을 읽고 깨끗한 상태에서 이어서 작업합니다. 교대한 에이전트는 이전 컨텍스트가 없는 깨끗한 상태에서 시작하기 때문에, 뒷부분을 대충 처리하는 문제가 사라져요.

참고: Context Reset 외에 Compaction(압축)이라는 방식도 있어요. Context Reset은 에이전트를 교체해서 깨끗한 상태로 시작하는 것이고, Compaction은 같은 에이전트가 계속 일하면서 이전 대화를 요약·압축하는 것이에요. Compaction은 대화의 연속성은 유지되지만, 컨텍스트 불안 자체를 해결하지는 못해요.

해결책 2. 자기 평가 편향 → Generator/Evaluator 분리

설계하는 AI(Generator)와 채점 및 검수하는 AI(Evaluator)를 완전히 분리합니다.

여기서 한 가지 의문이 생길 수 있어요. "채점하는 AI도 어차피 AI인데, 역시 후하게 주지 않을까요?" 맞는 지적이에요. 하지만 Anthropic이 발견한 핵심 인사이트는 이거예요:

"자기 작업을 스스로 비판하도록 만드는 것"보다
"별도의 채점자를 엄격한 기준으로 세팅하는 것"이 훨씬 쉽습니다.

콘텐츠를 만든 AI에게 "객관적으로 평가해봐"라고 하면 어렵지만, 콘텐츠 제작에 관여하지 않은 별도의 AI에게 명확한 채점 기준을 주고 "이 기준에 맞는지 검수해줘"라고 하면 훨씬 신뢰할 수 있는 결과가 나와요.

핵심은 Evaluator에게 구체적인 평가 기준을 정해주는 거예요. "잘 만들었는지 봐줘"가 아니라, "KPI 목표값과 표시된 숫자가 일치하는지, 면책 문구가 들어 있는지, 모바일에서 차트가 깨지지 않는지 확인해줘"처럼 명확한 기준을 제시해야 해요.

개념실전 패턴: 3-에이전트 구조 (Planner / Generator / Evaluator)

위에서 다룬 문제와 해결책을 하나의 구조로 만든 것이 3-에이전트 패턴이에요. AI에게 복잡한 작업을 시킬 때, 하나의 AI에게 모든 것을 맡기는 대신 기획/실행/검수 3단계로 역할을 나누면 컨텍스트 불안과 자기 평가 편향을 동시에 해결할 수 있어요.

Planner(기획자) → Generator(실행자) → Evaluator(검수자)
(기준 미달 시 Generator에게 재작업 요청)

역할하는 일
Planner (기획자)사용자의 요청을 구체적인 작업 명세로 변환합니다
Generator (실행자)실제 콘텐츠/결과물을 생성합니다
Evaluator (검수자)결과물을 평가하고, 기준에 미달하면 재작업을 요청합니다
3.1에서 살펴본 REXA 마케팅 에이전트 시스템에서는: Max = Planner, KAI = Generator, Luna = Evaluator 역할을 맡고 있어요.

개념핵심 교훈 3가지

교훈내용
1. 에이전트를 직접 관찰하라AI가 작업하는 과정을 직접 지켜보세요. 어디서 막히는지, 어떤 판단을 내리는지 확인하고, 원하는 결과가 나올 때까지 CLAUDE.md나 프롬프트를 조정하세요.
2. 복잡한 작업은 분해하고 전문화하라하나의 AI에게 모든 것을 시키는 대신, 기획/실행/검수처럼 역할별로 전문 에이전트를 배치하면 전체 성능이 올라갑니다.
3. 새 모델이 나오면 하네스 구조를 다시 점검하라AI 모델이 발전하면 불필요해진 구성요소는 제거하고, 새롭게 가능해진 기능을 위한 구성요소를 추가하세요. 점검하지 않으면 불필요한 절차만 쌓이게 됩니다.

체크포인트

  • 하네스 엔지니어링의 개념과 목적을 이해함
  • AI에게 일을 그냥 시키면 생기는 문제(컨텍스트 불안, 자기 평가 편향)를 이해함
  • 3-에이전트 패턴(Planner / Generator / Evaluator)을 이해함

3.4 [실습] 나만의 에이전트 만들기 (자율 실습 · 20분)

이 시간이 오늘의 하이라이트예요! 본인의 실제 업무를 AI-Native 방식으로 자동화하는 에이전트를 직접 만들어 볼게요. 20분 안에 완벽한 결과물보단, "다음 주에 이어서 키울 씨앗"을 심고 나가는 게 목표입니다.

Step 1 · 자동화할 작업 선택하기 (3분)

아래 중 하나를 고르거나, 본인만의 아이디어를 선택해 주세요.

옵션설명
A. 데이터 분석 레포트업무 KPI/지표를 자동으로 모아 HTML 대시보드로 만들기 (오늘 KAI 흐름 응용)
B. 디자인 작업 개선기존에 수작업으로 하던 디자인 작업을 클로드로 개선
C. 데이터 + 디자인 파이프라인데이터를 가져와서 자동으로 디자인 결과물 생성
D. 콘텐츠 호스팅 자동화수동으로 올리던 콘텐츠를 자동 게시
E. 나만의 아이디어다른 자동화하고 싶은 업무!
E를 선택한 경우 · 클로드 코드에게 아래와 같이 입력하면 업무를 정리할 수 있어요.
클로드 코드에 입력
"나는 [하고 싶은 업무]를 자동화하고 싶은데, 어떻게 시작하면 좋을지 모르겠어.
내 업무에 대해 질문해줘. 대화하면서 함께 정리하자."

Step 2 · 클로드와 함께 PRD 작성하기 (8분)

자동화할 작업이 정해졌으면, 아래 프롬프트를 클로드 코드에 입력해 주세요. 대괄호 [ ] 안의 내용은 본인의 상황에 맞게 바꿔서 입력해 주세요.

클로드 코드에 입력
"나는 [선택한 작업]을 자동화하고 싶어.

현재 상황:
- [현재 어떻게 작업하고 있는지]
- [어떤 부분이 반복적이고 시간이 오래 걸리는지]
- [최종 결과물은 어떤 형태인지]

이 작업을 자동화하기 위한 PRD를 작성해줘.
PRD에는 다음을 포함해줘:
1. 프로젝트 개요와 목적
2. 필요한 에이전트 역할 정의 (각각 이름, 역할, 담당 업무)
3. 작업 흐름 (파이프라인)
4. 입력 데이터와 최종 출력물
5. 품질 기준"
클로드가 PRD를 작성해주면, 내용을 읽어보고 수정이 필요한 부분을 대화로 요청하면 돼요.

Step 3 · 에이전트 1차 구축 (7분)

PRD가 완성되면, 아래 프롬프트로 실제 에이전트의 첫 번째 버전을 요청해 보세요.

클로드 코드에 입력
"이 PRD를 바탕으로 에이전트를 구축해줘.

구축 순서:
1. 먼저 CLAUDE.md를 만들어줘 (이 프로젝트의 규칙과 역할 정의)
2. 가장 핵심이 되는 파이프라인부터 만들어줘
3. 한 단계씩 테스트하면서 진행하자"

Step 4 · 테스트 & 한 번 다듬기 (2분)

에이전트가 만들어지면, 실제로 작동하는지 짧게 테스트해 보세요.

클로드 코드에 입력
"방금 만든 에이전트를 테스트해보자.
[테스트 데이터 또는 상황]을 입력으로 실행해줘."

결과물을 확인한 후, 개선이 필요한 부분이 있다면:

클로드 코드에 입력
"결과물을 보니 [개선할 점]이 있어.
[구체적으로 어떻게 바꿔야 하는지] 수정해줘."

스스로 점검해볼 질문들

아래 질문들은 클로드에게 입력하는 것이 아니라, 결과물을 보면서 스스로 점검하는 질문이에요.

  • "결과물의 품질이 내 기대에 맞는가?"
  • "아직 수작업인 단계가 남아 있는가?"
  • "다른 사람이 이 결과물을 바로 쓸 수 있는가?"

점검 결과 개선이 필요하면, 위의 테스트 & 개선 프롬프트를 반복해 주세요. 워크숍 이후에도 계속 키워나갈 수 있는 씨앗이에요.

체크포인트

  • 자동화할 작업을 선택함
  • 클로드와 함께 PRD 초안을 작성함
  • 에이전트 1차 버전을 구축하고 한 번 테스트함
  • 다음에 개선할 항목 1~2개를 메모함

부록실무 팁 & 참고 자료

실무 팁 — CLAUDE.md & 프롬프트 4선

CLAUDE.md 활용법

CLAUDE.md는 클로드 코드가 매 세션마다 자동으로 읽는 프로젝트 설정 파일이에요.

CLAUDE.md 없이CLAUDE.md 있으면
"나는 부동산 마케팅 기획자야. KPI 레포트를 만들건데, 두 계정은 합산하고, 면책 문구는 필수, 색상은 Deep Navy + Orange로..."

→ 매번 새 대화마다 같은 설명을 반복		 "이번 주 KPI 레포트 만들어줘"

→ 클로드가 이미 프로젝트 맥락을 알고 있어서 바로 작업 시작

CLAUDE.md에 담으면 좋은 내용

  • 프로젝트 개요와 목적
  • PRD (에이전트 구성, 파이프라인, 품질 기준)
  • 용어 규칙 (예: "ALWAYS use 워크숍, not 세미나")
  • 브랜드 톤앤매너
  • 금지 사항 (예: "NEVER use 확정수익, 원금보장")
CLAUDE.md는 프로젝트의 "헌법"과 같아요. 개별 프롬프트보다 우선 적용되며, 명시적으로 수정하지 않는 한 계속 유지됩니다.

CLAUDE.md를 프롬프트로 만들기

CLAUDE.md를 직접 작성할 필요 없어요. 클로드 코드와 작업하다가 아래 한 줄이면 됩니다.

클로드 코드에 입력
"지금까지의 내용을 CLAUDE.md에 저장해줘"

실무에서 바로 쓸 수 있는 프롬프트 4가지

1. UX가 어색할 때

클로드 코드에 입력
"10년차 UX 디자이너로서 이 제품의 사용자 흐름을 평가해.
문제점을 찾고, 개선안을 우선순위와 근거를 붙여서 제안해."

2. 뭘 먼저 고쳐야 할지 모를 때

클로드 코드에 입력
"이 제품의 PM으로서 아래 고객 피드백과 이탈률 데이터를 분석해.
지금 당장 손봐야 할 항목 3가지를 임팩트 순으로 뽑아."

3. 코드가 지저분해졌을 때

클로드 코드에 입력
"시니어 엔지니어로서 코드베이스를 리뷰해.
성능 병목, 중복, 접근성 이슈를 진단하고 리팩토링 계획을 잡아."

4. 출시 전 불안할 때

클로드 코드에 입력
"QA 리드로서 이 제품을 테스트해.
엣지 케이스, 에러 처리 누락, UI 깨짐을 심각도 순으로 정리해."
이 프롬프트들의 공통점: 역할을 명확히 지정하고, 구체적인 산출물을 요청합니다. 3.3에서 배운 Generator/Evaluator 분리를 프롬프트 레벨에서 활용하는 거예요.
